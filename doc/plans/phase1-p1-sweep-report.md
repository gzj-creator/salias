# Salias Phase 1 - P1 拓扑与 Payload 扫描报告

**执行日期**：2026-10-19  
**执行人**：Codex

## 一、执行摘要

本轮未复现 64 B 的稳定 6.5 Mmsg/s 基线，也未确认单一根因。1P1S 64 B 中位数为
9.492 Mmsg/s，1P2S 为 6.560 Mmsg/s，退化 30.89%，但 1P1S CV=39.16% 且低于计划中
“>10 Mmsg/s”的订阅者扫描判据；同一批 1P2S 256 B 中位数为 15.704 Mmsg/s。Payload
扫描在 128→192 B 出现 +167.46% 的明显断点，192 B 中位数 17.064 Mmsg/s；56 B 仅比
64 B 快 6.63%，不支持 H2 的 >20% 对齐假设。当前最可信的方向是“负载相关的高吞吐区
与显著系统噪声并存”，下一步应优先复核 64/128/192 B 边界和运行间双峰稳定性，而非
直接实施产品优化。

## 二、P1.1 拓扑扫描结果

执行 44 次（4 次预热、40 次正式）。每组 10 个正式轮次、50M 消息/轮，无 timeout、
OOM、计数不一致或校验失败。宿主为 4 vCPU，因此按计划跳过需要 CPU4 的 1P3S。

### 2.1 绝对吞吐

| 拓扑 | 64 B 中位数 (Mmsg/s) | 64 B CV | 256 B 中位数 (Mmsg/s) | 256 B CV |
|---|---:|---:|---:|---:|
| 1P1S | 9.492 | 39.16% | 15.546 | 9.33% |
| 1P2S | 6.560 | 26.53% | 15.704 | 26.56% |
| 1P3S | 未执行（4 vCPU） | - | 未执行（4 vCPU） | - |

### 2.2 相对退化

| 过渡 | 64 B 退化 | 256 B 退化 | 判定 |
|---|---:|---:|---|
| 1P1S → 1P2S | 30.89% | -1.02%（+1.02% 吞吐） | 64 B 刚越过 30%，256 B 无退化 |
| 1P2S → 1P3S | 未执行 | 未执行 | CPU 资源不足，无法判断线性性 |

**结论**：64 B 的退化率刚超过计划阈值，但 1P1S 中位数低于计划设定的 10 Mmsg/s，
而且两组 64 B 都出现明显高值离群轮（1P1S 两轮 18.2/19.9 Mmsg/s，1P2S 一轮
12.0 Mmsg/s）。因此 P1.1 支持“64 B 对拓扑敏感”，不足以单独确认订阅者扫描是稳定
根因；发布侧与测量扰动都未被排除。分析器的判定因此是 `unclear`，不是
`subscriber-scanner bottleneck`。

## 三、P1.2 Payload 扫描结果

执行 54 次（9 次预热、45 次正式），固定 1P2S、50M 消息/轮、每组 5 个正式轮次；
全部成功。帧步长由 `src/core/frame/codec.hpp` 的 `8 + align_up(payload, 8)` 计算。

### 3.1 吞吐-Payload 曲线

| Payload (B) | 帧步长 (B) | 中位数 (Mmsg/s) | CV | 对齐性 |
|---:|---:|---:|---:|---|
| 48 | 56 | 6.155 | 4.91% | 56 mod 64 |
| 56 | 64 | 6.832 | 5.59% | 64 B 倍数 ✓ |
| 64 | 72 | 6.407 | 14.04% | 8 mod 64 |
| 72 | 80 | 7.382 | 6.45% | 16 mod 64 |
| 80 | 88 | 6.268 | 30.64% | 24 mod 64 |
| 96 | 104 | 6.350 | 4.85% | 40 mod 64 |
| 128 | 136 | 6.380 | 8.85% | 8 mod 64 |
| 192 | 200 | 17.064 | 1.85% | 8 mod 64 |
| 256 | 264 | 11.348 | 35.28% | 8 mod 64 |

### 3.2 断点检测

- 128→192 B 中位数变化 **+167.46%**，是唯一超过 50% 的相邻断点；192 B 五轮范围
  16.514–17.334 Mmsg/s，稳定性最好。
- 192→256 B 中位数下降 33.50%；256 B 出现 15.4–15.7 Mmsg/s 的高值轮与
  7.4/7.6 Mmsg/s 的低值轮，因而中位数 11.348、CV 35.28%。这说明“高 payload 快”
  不是单调、稳定的规律。
- 48–128 B 基本处于 6.2–7.4 Mmsg/s 平台；80 B 与 64 B 虽为不同步长，但都受单轮
  高值影响，不能据此建立对齐因果。

**结论**：存在 128→192 B 断点，但没有证据支持 H2。56 B（步长 64）仅比 64 B
（步长 72）快 **6.63%**，远低于 20% 门槛；同时 72 B 也比 64 B 快，不能由单一
64 B 对齐解释。192 B 异常高吞吐更值得作为“高吞吐区机制”追查。

## 五、推荐下一步

**推荐：进入“P1 边界复核 / Phase 2 前置稳定性实验”，暂不直接实施 Phase 2A/2B/2C 产品改动。**

**理由**：

1. 64 B 的 30.89% 只刚好越过阈值，且两组 CV 为 39.16%/26.53%；先排除双峰与
   运行顺序对拓扑结论的影响，成本低、能决定后续方向。
2. 128→192 B 断点稳定（192 B CV 1.85%），但 256 B 不稳定，说明存在可测量的
   payload 机制；用 128/144/160/176/192 B 和重复顺序实验可定位边界。
3. H2 已排除；H3 仍未被隔离。只有在复核后仍显示发布侧受限，才值得进入
   Phase 2B 的单发布者快速路径实验。

**备选方案**：若边界复核仍呈现双峰，先做系统噪声与调度隔离实验（不同 Nice、
CPU 独占/共享、固定轮次顺序），再讨论批量进度或 Guard 优化。
