## 7. 产品化建议

### 7.1 如果判定为"强候选"

**候选方案：**

**方案 A：** 保留 `claim.commit()`，claim 持非拥有端点裸指针
- 优点：源码改动小
- 缺点：契约风险高，use-after-free 未由类型系统保护

**方案 B：** 改为 `publisher.commit(claim)` 的 Aeron 风格 API
- 优点：所有权关系更清晰
- 缺点：需要 API 迁移和 ABI 变更

**推荐：** [待填充，需用户批准]

### 7.2 如果判定为"可能有贡献"或"拒绝假设"

**后续方向：**
- 转向 single-writer/MPSC 协调路径诊断
- 或调度和宿主噪声诊断
- 不修改 claim 生命周期

## 8. 边界与局限

1. **诊断变体不是产品实现**：borrowed claim 涉及生命周期假设，绝不能直接作为产品修复。
2. **可能的其他成本来源**：即使引用计数是主因，libc 运行时路径、调度噪声仍可能贡献剩余成本。
3. **产品化成本**：需要 API 变更（方案决策）、可能的 ABI 变更、生命周期契约文档。
4. **不包含 batching**：本计划默认 batch=1；未来批量路径必须另立计划并单独验收尾部。
