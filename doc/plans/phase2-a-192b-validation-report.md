# Salias Phase 2-A：192 B 配置 100 轮验证报告

**执行日期**：2026-10-20（Asia/Singapore）  
**执行人**：Codex  
**结论**：**未通过“已观测最佳配置”推荐门槛**。完整 100 轮中高模式为 **69/100
（69.0%）**，未达到 **85%+**；全体中位数为 **16.4806 Mmsg/s**，满足 `>16 Mmsg/s`。
相对历史 192 B 基线没有统计显著退化，但也没有改善。

## 一、验收结果

| 指标 | 本轮结果 | 门槛 | 判定 |
|---|---:|---:|---:|
| 高模式率（`>=15 Mmsg/s`） | **69/100（69.0%）** | `>85%` | **未通过** |
| 全体中位数 | **16.4806 Mmsg/s** | `>16 Mmsg/s` | 通过 |
| 仅高模式轮的 69 轮中位数 | **16.6859 Mmsg/s** | `>15 Mmsg/s` | 通过 |
| 高模式范围 | 15.3481–17.3518 Mmsg/s | 参考项 | - |
| 全体轮次范围 | 5.07568–17.3518 Mmsg/s | 参考项 | - |

全体 100 轮包含 16 轮 `<10 Mmsg/s`、15 轮 `10–15 Mmsg/s` 和 69 轮高模式。
高模式轮的 Q1/Q3 为 16.4490/16.9671 Mmsg/s，高模式自身较集中；整体离散度主要由
低频低吞吐轮造成，全体 CV 为 25.37%，高模式子集 CV 为 2.59%。

## 二、与历史基线的比较

用户任务中的“64 B 的 72% 高模式率”口径有误。**72%（288/400）是 192 B、50M
消息的历史高频基线**，与 64 B 的约 6–7 Mmsg/s 低吞吐问题不是同一组样本。

按 192 B 历史高频基线做两比例比较：

| 项目 | 历史 192 B 基线 | 本轮 192 B | 差异 |
|---|---:|---:|---:|
| 高模式 | 288/400（72.0%） | 69/100（69.0%） | **-3.0 pp** |
| 全体中位数 | 16.6187 Mmsg/s | 16.4806 Mmsg/s | -0.83% |
| 仅高模式轮中位数 | 16.8356 Mmsg/s | 16.6859 Mmsg/s | -0.89% |

双侧合并两比例 z 检验：`z=-0.5938`、`p=0.5527`。因此本轮与 400 轮历史基线之间
**没有统计显著的高模式率差异**；不能据此声称 192 B 进入率发生了回归，也不能声称它
达到了 85% 推荐门槛。

作为条件更接近的敏感性对照，历史基线的前 5 组（同为 no-sleep）为 75/100（75.0%），
本轮为 69/100（69.0%），差异 -6.0 pp，`p=0.3447`，仍不显著。该切片只作为敏感性
分析，不替代原定的 400 轮历史基线。

## 三、测量条件与完整性

- 客户端：冻结 v3.0.0 `salias_ipc_compare.uninstrumented`；
- 客户端 SHA-256：
  `3f8fc6957ce56483d7051dd6625f44fd8f755d57a66d04e1e5efa48e65b9c7da`；
- 负载：192 B、1P2S、50M 消息/轮、1 MiB ring、batch 1、poll-limit 64；
- 发布路径：冻结客户端内置 claim；
- 调度：coordinator CPU0；consumer0 CPU1、consumer1 CPU2；publisher CPU3；
- 资源：systemd user unit，CPUs 0–3、Nice 5、MemoryHigh 640M、MemoryMax 704M、
  swap 0；
- 分组：5 组 × 20 轮 = 100 个有效测量轮，组间等待 0 秒。

实际执行使用现有 `high-frequency-stability-runner.py`。原示例
`verify-instrumented-192b.py` 不接受 `--payload`，且 `--rounds` 上限为 30，不能直接完成
100 轮；示例分析脚本另有缩进及 `if name == 'main'` 错误，因此未创建该脚本。

正式完整样本目录：
`build/benchmarks/p2a-192b-validation-20261020-191535/`。
该目录包含 100 份 stdout/stderr、逐轮 JSON、组摘要和分析结果；319 个文件中的 318 个
原始证据由 `SHA256SUMS` 校验通过，分析输出按 runner 约定不进入清单。100 份 stderr 均为
systemd 成功摘要，没有 benchmark 错误；无 OOM/high/max 内存事件、没有 CPU throttling、
也没有遗留 benchmark 进程。

另保留一次启动门禁提前中止的样本：
`build/benchmarks/p2a-192b-validation-20261020-191432/`。它只完成 3 轮
（14.2939、14.9313、7.35988 Mmsg/s），是 **不完整诊断样本**，不纳入 100 轮统计。
正式 100 轮关闭了“连续低模式即中止”，以免截断真实低模式轮次。

## 四、分组观察

| 组 | 高模式 | 全体中位数 |
|---|---:|---:|
| 0 | 18/20 | 16.8474 Mmsg/s |
| 1 | 9/20 | 11.0247 Mmsg/s |
| 2 | 11/20 | 15.5957 Mmsg/s |
| 3 | 15/20 | 16.4951 Mmsg/s |
| 4 | 16/20 | 16.4696 Mmsg/s |

第一组 18/20，支持冻结客户端确实能进入高模式；但第二组的连续低模式拖低了整体进入率。
100 轮中共有 34 次高/低状态切换，平均高模式连续段 3.8 轮、低模式连续段 1.8 轮，
最长高/低连续段分别为 10/6 轮。该现象与此前 400 轮结论一致：高模式本身集中，但入口
不稳定，不能用单次或少量轮次代表稳定配置。

## 五、判定与下一步

**判定：未通过 P2-A 的 192 B 推荐资格。** 因此不将 192 B 写成“已稳定达到 16 Mmsg/s”
或“85% 以上高模式”的推荐配置。可以保留的事实是：在冻结 v3.0.0 与上述固定条件下，
192 B 的高模式轮中位数约 16.7 Mmsg/s，但 100 轮仅有 69% 进入高模式。

建议下一步进入 **P2-C（高模式率优化）** 或先定位低模式入口的系统/运行时变量。若要继续
验证 192 B，应使用更长或分块重复实验，并报告全体轮次与高模式子集两个口径，不能只挑
高模式轮。此次结果不否定 claim 路径修复本身，也不把轮次低模式误判为产品功能错误。
