## 不变的验收条件

- 原样使用 `tools/hft_acceptance/acceptance.cpp`，不修改计时、输入速率、完整性检查或采样逻辑。
- 主要时延仍为计划到达至 subscriber，逐订阅者判断，包含发布前积压和背压；不使用 claim 后时延替代。
- 两 publisher，2P1S/2P2S、64 B/256 B，4 MiB 每 producer 环，128 KiB 发布窗口，batch=1、poll=64，显式绑核。
- 稳态总 1M msg/s；突发每秒前 100ms 为 4M/s、其余 1M/s。这是合成负载假设。
- 完整性、输入完成、退出与注册代际安全优先；不能通过忽略慢消费者、丢弃可靠消息或削减输入换取指标。
- 50 µs 是暂定单跳验收预算，分别报告 p99/p99.9；未完成负载或任一订阅者未达标均不能称通过。

## 验收顺序

1. 冻结原二进制；从 Git HEAD 导出源码，用同一当前编译器重建独立基线，避免旧构建工具链混杂。
2. 审查子 agent 的最小补丁及反例测试，执行 Release 与适用 sanitizer 回归。
3. 相同配置逐一串行运行 baseline/candidate/candidate/baseline，原始桶按配置、版本、订阅者独立合并。
4. 候选版再运行八阶段各 225 秒的总计 30 分钟验收；短 A/B 不代替长测。
5. 对照原始数据复算完整性、消息量、最差订阅者尾延迟、背压，披露回退和环境限制。

A/B 工具为 `tools/hft_acceptance/run_tail_ab.sh` 与 `summarize_tail_ab.py`；
本轮原始证据曾写入 `doc/benchmarks/2026-10-18/tail-optimization/`；现已完成复核并按用户要求
清理临时文件，保留最终 Markdown 及[精简结果归档](../../benchmarks/2026-10-18/performance-results.json)。

## 判断边界

一次短 syscall 追踪确认了进程探测路径频繁执行，但追踪干扰性能，不作为性能通过证据。
减少探测需要保留 PID 复用、注册代际变化、注销并发、死消费者回收以及可靠背压语义。
只把已经由 A/B 和长测验证的结果写为收益；不预先承诺达到 50 µs，亦不把尖峰直接归因于 KVM。

## 进程探测的独立诊断

长测后另跑 2P2S/256 B 突发 syscall 诊断，每版本两次、每次2秒；不与长测并行。
原始 trace 已清理，诊断计数保留在
[精简归档](../../benchmarks/2026-10-18/performance-results.json) 的 `syscall_diagnostic` 项。

- 基线两个诊断的 `/proc/<pid>/stat` 打开次数分别 **11,021 / 10,563**。
- 候选分别 **757 / 241**；与健康游标无需 probe 的80实例定向 fixture 一致，证明目标调用减少。
- 跟踪本身改变运行时序；基线诊断还有未发送输入，不能把上述计数比率当成真实环境的延迟收益。
  性能结论只看未跟踪 A/B 和长测，不能把“probe 减少”写成“尾延迟稳定下降”。
